## 2. 규칙 적용 방식

Codex의 프로젝트 진입점은 루트 `AGENTS.md`다. 이 파일에서 상황별 `.claude/rules/*.rule.md` 원문을 명시적으로 읽도록 연결한다. `.claude`의 규칙 파일이나 임의의 `.codex/rules` 폴더가 자동 로드된다고 가정하지 않는다. [공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

Claude의 개인 설정·권한 허용 목록·MCP 인증정보를 Codex에 복제하지 않는다. 실제 도구와 권한은 현재 세션의 설정을 따른다. 문서의 오래된 도구 호출명은 현재 도구에 맞게 대응한다. Figma 작업은 설치된 Figma 스킬의 필수 선행 절차도 함께 따른다.

기존 규칙 본문은 원본에 유지하며, 이 문서는 현재 사용자 범위와 실행 환경의 차이만 보완한다. 규칙 변경 시 두 벌을 수정하지 않고 원본과 `AGENTS.md` 연결·보완 항목의 정합성을 확인한다.

## 3. 작업별 모델과 추론 강도

사용자 요구는 작업에 따라 모델을 선택하는 것이다. 다음은 이 프로젝트의 선택 기준이며 자동 라우팅 설정이 아니다. 실행 환경에 실제 노출된 모델·추론 강도만 선택한다. [공식 모델 선택 안내](https://learn.chatgpt.com/docs/models)

| 작업 | 모델 후보 | 추론 강도 기준 |
|------|-----------|----------------|
| 명확한 문구·문서·경로 정리, 반복 수정 | `gpt-5.6-luna` | low |
| 단일 컴포넌트·일반 반응형 구현·관련 테스트 | `gpt-5.6-terra` | medium |
| 복수 화면 정합성, 어려운 버그·SSR/CSR·FSD 판단 | `gpt-5.6-sol` | high |
| 여러 자료의 충돌, 복합 3D/성능 문제, 큰 변경의 종합 검토 | `gpt-6-astra` | high, 해결 난도에 따라 xhigh |

간단한 작업으로 돌아오면 비용·응답 시간을 고려해 다시 낮은 설정을 선택한다. 위 기준은 프로젝트 운영 제안이며 특정 모델의 품질을 보장하지 않는다. 모델 가용성과 이름은 바뀔 수 있으므로 실제 선택기와 최신 공식 문서를 우선한다.

현재 세션에는 실행 중인 주 에이전트의 모델을 직접 바꾸는 도구가 없다. 전환이 필요하면 권장 모델과 이유를 짧게 안내하고 사용 가능한 현재 모델로 허용된 작업을 계속한다. IDE에서는 입력창 아래 모델 선택기를, CLI에서는 `/model`을 이용할 수 있다. 전환을 확인하지 못한 상태에서 변경했다고 보고하지 않는다.

`model`과 `model_reasoning_effort` 설정은 모델·추론 설정 항목이지 작업 유형별 자동 전환 규칙이 아니다. 전역 설정을 임의로 덮어쓰지 않는다. 모델을 바꾸기 위한 목적으로 하위 에이전트나 별도 Codex 프로세스를 우회 실행하지 않는다. [공식 설정 안내](https://learn.chatgpt.com/docs/config-file/config-basic)

## 4. 변경과 실행 절차

1. 작업 트리·브랜치·대상 파일과 관련 규칙을 확인한다. 기존 사용자 파일은 보존한다.
2. 기여 규칙에 따라 작업 브랜치에서 변경한다. 브랜치 이름·전환은 현재 진행 작업을 고려하며, 다른 기능 브랜치의 미머지 커밋을 PR에 섞지 않는다.
3. 요구 화면과 PC/Mobile Figma 노드를 확인한다. UI 임의 축소·새 기능 추가를 피하고, 결정에 필요한 실제 불명확성만 확인한다.
4. FSD·토큰·공용 UI 규칙에 맞춰 구현하고 작업 범위에 맞는 검증을 수행한다.
5. 변경 diff와 기존 사용자 변경의 보존 여부를 확인하고, 검증 결과와 미확인 사항을 보고한다.

현재 명령은 `pnpm dev`(3001), `pnpm start`(3001), `pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`다. 명령을 실행하기 전에 `package.json` 변경 여부를 확인한다.

dev 서버를 띄우기 전에 포트·프로세스·프로젝트 경로를 확인한다. 포트 충돌 시 자동으로 다른 포트를 사용하지 않는다. 자신이 실행한 해당 프로젝트 서버만 정리하며, `node.exe` 또는 Next 프로세스 전체를 일괄 종료하지 않는다. 최신 코드가 실제 검증 주소에서 제공되는지 확인한다.

`next.config.mjs`는 `BUILD_DIST_DIR`로 빌드 출력 분리를 지원한다. 실행 중 서버와 `.next` 충돌을 피해야 하면 이를 검토하되, 출력 위치·생성 파일을 관리하고 경로 확인 없이 재귀 삭제하지 않는다.

## 5. 변경 종류별 검증

| 변경 종류 | 검증 |
|-----------|------|
| 문서만 변경 | 문서 정보·변경 이력, 로컬 링크와 원본 규칙 11종 연결, 현재 코드/지시와의 정합성, `git diff --check` |
| 기능·버그 수정 | 타입·린트, 관련 테스트와 실패/경계 사례, 원본 테스트 규칙 |
| UI 화면·Figma 구현 | 타입·린트·빌드 및 영향 테스트/회귀, 실제 렌더와 Figma 대조, 360/767/768/1280px 검증 |
| Phase 완료 | phase-review 원문의 전체 자동화·회귀·수용 기준 대조·검토 기록 |

브라우저 스크린샷을 우선한다. 도구가 없어 서빙 DOM으로 최소 검증할 때는 클래스뿐 아니라 생성 CSS와 미디어 쿼리도 확인한다. DOM 검사만으로 픽셀 정합성이나 터치·스크롤 동작을 검증했다고 보고하지 않는다.

원본 시각 규칙의 단일 서버·최신 렌더 확인·변경 후 재검증 취지는 유지한다. 지정 포트는 오래된 3000 대신 현재 스크립트의 3001을 적용한다. 문서 변경만으로 서버를 기동하거나 UI 테스트를 새로 만들 필요는 없다.

## 6. 파일·인증정보 관리

- `.env*`, `.npmrc`, `.mcp.json`, 개인 설정의 실제 비밀값을 출력·복사하지 않는다. 환경변수 참조만 공유한다.
- 작업과 관계없는 미추적 이미지·PDF·개인 파일을 삭제하거나 스테이징하지 않는다.
- Git 변경은 파일별로 검토한다. `git add -A`, `git commit -a`로 인증정보나 다른 작업을 포함시키지 않는다.
- 샌드박스가 `.git` 쓰기 등 필요한 작업을 막으면 정해진 승인 절차를 사용한다. 다른 도구나 경로로 우회하지 않는다.
- 실행하지 않은 테스트·조회할 수 없었던 저장소·미확인 디자인은 명시한다. 과거 인수인계의 PASS를 새 검증 결과로 재사용하지 않는다.
